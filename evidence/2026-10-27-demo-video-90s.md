## The CLI pin was moved, and the move was verified

`npx hyperframes@latest upgrade --project . --check` reported the pins would move
**0.8.186 → 0.8.206**. The rule for taking a bump is to apply it and then verify with
`hyperframes check`; unlike the 2:00 session, a full check could run here, so the bump was taken
and verified **before any of the re-cut was written**: `npx hyperframes@latest upgrade --project .`,
then `npm run check` against the unmodified 2:00 project, which passed with the same single
`composition_file_too_large` warning it had on 0.8.186. `video/package.json` now pins
`hyperframes@0.8.206` in all four scripts.

A passing check confirms the compositions still validate on the new version. It does **not**
confirm that rendered output is frame-identical to the old pin, and since this cut has not been
rendered at all, nothing here claims it is.

## The narration — a recorded run

```
cd video
HYPERFRAMES_PYTHON=~/.venv/bin/python HYPERFRAMES_PIN=hyperframes@0.8.206 ./tools/tts.sh
```

`tools/tts.sh` reads `tools/narration.json` and runs, per line:

```
npx hyperframes@0.8.206 tts "<line>" --voice af_heart --speed 1.0 --output assets/vo/<id>.wav --json
```

**Twenty-three lines, 191 words**, one `.wav` each in `video/assets/vo/`, voice **`af_heart`**
(Kokoro-82M, run locally) — the same voice and speed as the 2:00 cut. The voice covers
**62.208 s of the 90 s**. `n01` and `n02` are the 2:00 cut's files unchanged, because their text is
unchanged; the other 21 were generated for this cut. The 2:00 cut's surplus lines `n24`–`n32` are
no longer mounted and were deleted from `assets/vo/`; they are in git at `c86ba4c`.

Each line's caption is that line word for word and carries the same `data-start`, so a caption
cannot drift from the voice; a caption holds until the next line speaks, so text never leaves the
frame. `video/STORYBOARD.md` prints all 23 lines with their in-points and measured lengths.

`video/index.html` is **generated** by `python3 tools/build_index.py`, which reads each `.wav` for
its true length and **refuses to write** if a line runs into the next one or past the end of its
scene. It accepted every anchor in this cut on the first run. `assets/vo/narration-full.wav` is the
23 files laid onto one 90 s track at their film times; **the transcription still has not run**, for
the reason the 2:00 cut's evidence gives (no whisper-cpp, and the npm install of a backend is
refused by this project's script policy), and the captions do not rest on it.

### The generator, and one thing to watch

`build_index.py` is deterministic: run back to back against the delivered tree it writes the same
bytes, and the delivered `video/index.html` is sha256
`36a7cbd42de9e6affd0237517949a7b17e77cf053e9260f9a29714697fba2ff0`.

**The file did change once between generator runs in this session, with a Studio preview session
in between**, and the cause was not isolated — the Studio writes a project's edits back to disk, so
that is the candidate, but nothing here proves it. Treat it as a reason to re-run
`python3 tools/build_index.py` after any preview session and before a render, not as a finding. The
2:00 cut's recorded `index.html` hash no longer applies to anything: `TOTAL`, `SCENES`, `ANCHOR`
and the music lane all changed.

## The render — run here, and measured

It was run under the memory the machine had, not the memory the rule wants. The standing
instruction is to hand over the command rather than start a render under about 3 GiB free; the
operator read that and said to render anyway. So this is a render performed against the rule, on
purpose, and it finished clean.

`free -m` at the moment the render started: **404 MiB free, 2,270 MiB available**, 4.0 GiB already
in swap. The renderer noticed for itself and said so:

```
[Render] Low-memory render profile active: screenshot capture, auto-worker calibration skipped.
         totalMemMb: 7730, thresholdMb: 8192
```

The command, run from `video/`, after regenerating the generated index:

```
python3 tools/build_index.py
npx hyperframes@0.8.206 render --output out/unstirred-demo.mp4 --fps 30 --quality delivery \
    --workers 2 --skill general-video
```

`index.html` as rendered was sha256
`36a7cbd42de9e6affd0237517949a7b17e77cf053e9260f9a29714697fba2ff0`.

**The capture path was `screenshot`, not the fast one.** The expectation recorded above — that
`chrome-headless-shell` being installed would buy the fast path — was wrong, and the reason is
worth keeping: the renderer auto-selected screenshot capture because of the compositions
themselves, not because of memory or a missing binary.

```
Auto-selected screenshot capture mode for render compatibility
  reasonCodes: ["iframe"]
  reasons: ["Detected <iframe> in the composition DOM. Nested iframe animation is routed through
            screenshot capture mode for compatibility."]
...
Screenshot capture (slower): BeginFrame did not run.
```

Five scenes mount real pages from `assets/site-pages/` in `<iframe>`s, so this cut can only ever
take the slow path. That is a property of the design, and it is the right trade: the browser
frames are the real site rather than a drawing of it.

### One warning that did not bite, and should still be fixed

The compiler could not pre-download the one CDN script the composition loads:

```
WARNING: Failed to download CDN script:
  https://cdn.jsdelivr.net/npm/gsap@3.14.2/dist/gsap.min.js (TypeError: fetch failed)
  The render may fail if this script is required (e.g. GSAP).
```

This was checked rather than assumed. The URL answers `200` with 72,779 bytes from this machine,
the render browser loaded it, and the delivered frames show motion that only exists if GSAP ran —
staggered reveals, the strikethrough pass, the camera zoom in the newcomer scene. So it was a
transient failure in the compiler's own pre-fetch, not a dead dependency.

It is still a real hazard: `index.html` loads GSAP over the network at render time, and had that
blip lasted, the render would have produced 2,700 static frames and reported success. Vendoring
`gsap.min.js` into `video/assets/` removes a network dependency from a deterministic pipeline.
Not done here, because changing `index.html` mid-render would have invalidated the hash recorded
above.

sha256 unchanged at `9d1d7acb820e2343119fa8d818f3859da78c976d3a92f3522f4a86c081522399`. The 1:30
render's own log is `out/render-90s.log`.
