## What the PIR client is pinned to, and why that pin

`vote-nullifier-pir` HEAD (dc3ef4f, "Prepare Common v3 PIR library releases") moved the whole PIR
stack to Zakura Common 3.0.0. Its LRZ cohort is pasta_curves 0.6 / orchard 0.16 / halo2_proofs
0.4. Unstirred is on voting-circuits 0.12.2, whose LRZ cohort is pasta_curves 0.5 / orchard 0.15 /
halo2_proofs 0.3. The two cannot share a field-element type, so a proof returned by a HEAD client
could not be copied field for field into `voting_circuits::delegation::ImtProofData` at all.

Tag `v0.12.3` (commit ac15ed2) is the last commit before that bump, and it pins
`voting-crypto-deps =0.2.4`, the same facade version Unstirred uses. Its `upstream` feature
selects `voting-crypto-deps/lrz-vct`, which is part of the `lrz` set Unstirred already enables, so
the two unify on one pasta_curves 0.5.

The pin is that commit, taken from crates.io so a clean clone needs nothing but the registry and
so the eventual 0.1.0 publish stays possible (crates.io rejects git and path dependencies). Every
`.rs` file of the three crates was checked byte-for-byte against the tag before the pin was taken:

| Crate | Version pinned | Files compared against `v0.12.3` | Result |
|---|---|---|---|
| `pir-client` | =0.7.4 | `src/lib.rs`, `src/transport.rs` | identical |
| `pir-types` | =0.6.4 | `src/lib.rs`, `src/fp_utils.rs`, `src/tier0.rs`, `src/tier1.rs` | identical |
| `imt-tree` | =0.5.4 | `src/lib.rs`, `src/hasher.rs`, `src/proof.rs`, `src/tree/mod.rs`, `src/tree/tests.rs`, `src/test_helpers.rs`, `benches/tree_build.rs` | identical |

`valar-ypir` and `valar-spiral-rs` were then pinned down to =0.2.0 and =0.5.2, the versions in
that commit's own `Cargo.lock` (checksums match), because the YPIR parameters are what the client
and the server have to agree on.

**A local `nf-server` for this to talk to must therefore be built from `v0.12.3` (ac15ed2), not
from HEAD.** No live lookup is recorded yet, so nothing here claims one works.

## What the lookup does

1. `GET /root` on the PIR server, which is a public request about a public snapshot. The answer is
   refused unless it is the ironwood pool at dataset version 2, on the gate's network, at exactly
   the gate's h1, with the tree layout this build speaks.
2. If `--expected-h1-root` was given, it is checked against that advertised root **before any
   query is sent**, so a server holding the wrong snapshot is never queried.
3. Each selected note's nullifier is derived from the wallet's own Ironwood (Orchard) full viewing
   key, read-only, and handed to `pir-client`, which puts it on the wire only inside a YPIR
   ciphertext. There is no plaintext code path.
4. Each returned proof is copied field for field into `voting_circuits::delegation::ImtProofData`
   (`root`, `nf_bounds`, `leaf_pos`, `path`), its root is checked against the agreed h1 root, and
   the non-membership path is walked out of circuit against the note's nullifier.
5. A server that cannot be reached, or will not answer, is `PIR_UNAVAILABLE`: inconclusive,
   retryable, and never a reason to ask any other way.
