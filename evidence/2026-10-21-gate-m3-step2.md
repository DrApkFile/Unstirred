## What this run does not prove

- **That the page looks right.** Nobody has opened it in a browser; there is none in the session
  that built it. `ui/render.js` was run against a minimal DOM shim under node, which shows that
  every act renders and prints the words it should, and A44 shows the document carries the act
  unchanged. None of that is a look at the thing. The stage is a fixed 1920×1080 with rows that can
  only shrink, so content that does not fit clips inside its own panel rather than breaking the
  frame; whether anything clips is unverified.
- **That `render(state)` produces the right DOM.** A44 checks that every act parses into the state
  contract the renderer reads, that the document carries it unchanged, and that the document has no
  network call site. Executing the renderer would need a JavaScript engine, which this workspace
  does not depend on and this gate does not run.
- Nothing about the Zcash network. The only real-testnet values in this run are the replay acts',
  and they are copies of `evidence/2026-10-20-two-room-knock.txt`, which is the recorded run that
  settles them.
- Not that the live poller works against a running gate: A02c and A44 read the documents the gate
  serves, and the live path's two routes are covered as JSON (A43 for the feed, A34 and the room
  log for the log). A browser polling them has not been watched.
- **The git-grep half of the leak scan cannot see this step's new files**, because they are
  untracked: `git grep` skips untracked files. They were read for key material and holder
  identifiers by hand instead, and hold neither — the only addresses in them are `127.0.0.1` in the
  gate's own recorded root-source config and the test fixture's `127.0.0.1:0`. The scan will cover
  them the moment they are committed.
- Not that a challenge expires, that two independent root sources agree, or that a running process
  keeps a secret off a channel: the same limits as the M3 step 1 run.
